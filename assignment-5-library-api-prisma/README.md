# Library Book Management API: Prisma ORM and PostgreSQL

**Session 6 assignment: Library Book Management API, upgraded with Prisma ORM and PostgreSQL.**

This is the Library API from [`assignment-3-library-book-api`](../assignment-3-library-book-api) (Express 5, TypeScript, Zod). The in-memory array is replaced with a PostgreSQL database accessed through **Prisma ORM 7**. The endpoints, request bodies, responses, status codes and error messages are unchanged.

## Summary: How It Works

**What changed:** before, books lived in an array in the server's memory and were lost on every restart. Now they are rows in a PostgreSQL table, so they survive restarts and can be seen in pgAdmin.

**Request flow** (same as before, with a database at the end):

```text
Request -> Route -> validateBody (POST/PATCH) -> Controller -> Service -> Prisma Client -> PostgreSQL
                         |                           |            |
                         +------ any error thrown ---+------------+--> errorHandler -> JSON error
```

**Only two layers changed:**
- **Service:** uses `prisma.book.findMany / findUnique / create / update / delete` instead of array methods. Every function is now `async`, because a database call takes time and returns a Promise.
- **Controller:** each handler is `async` and `await`s the service. Express 5 sends errors from async handlers (rejected Promises) to the error handler automatically, so no `try/catch` is needed there.

Routes, Zod schemas, middlewares and error classes are the same files as in assignment 3. That is why the API contract did not change.

**Prisma pieces:**
- [`prisma/schema.prisma`](prisma/schema.prisma) describes the `Book` model. It has exactly the 5 fields of the API's `Book`, so the database row and the JSON response have the same shape.
- **Migrations:** `prisma migrate dev` turns the schema into SQL ([`prisma/migrations/`](prisma/migrations/)) and applies it. The SQL is committed, so every database gets the same table.
- **Prisma Client:** a typed client generated from the schema. `prisma.book.create(...)` only accepts valid fields and returns a typed `Book`.
- **Driver adapter:** Prisma 7 connects through `@prisma/adapter-pg` (the `pg` driver). The app creates **one** shared client in [`src/db/prisma.ts`](src/db/prisma.ts). Each client holds a connection pool, so one client per request would run out of connections.

**404 on update and delete:** `prisma.book.update` and `delete` throw error code `P2025` when no row matches. The service turns that into the same `NotFoundError` ("Book with id 999 not found") as before. This takes one query, instead of a "find, then update" pair that could be wrong if another request deleted the book in between.

## Database Schema

```prisma
model Book {
  id        Int     @id @default(autoincrement())
  title     String
  author    String
  genre     String
  available Boolean @default(true)

  @@map("books")
}
```

The migration Prisma generated from it ([`migration.sql`](prisma/migrations/20261128105419_init/migration.sql)):

```sql
CREATE TABLE "books" (
    "id" SERIAL NOT NULL,
    "title" TEXT NOT NULL,
    "author" TEXT NOT NULL,
    "genre" TEXT NOT NULL,
    "available" BOOLEAN NOT NULL DEFAULT true,

    CONSTRAINT "books_pkey" PRIMARY KEY ("id")
);
```

- `id` is generated by PostgreSQL (`SERIAL`). Zod still rejects an `id` sent by the client.
- `TEXT` has no length limit, like the Zod schemas, so a valid request can never fail in the database because of length.

## API Contract (unchanged)

Base URL: `http://localhost:3000/api/books`

| Method | Path | Description | Success | Errors |
|---|---|---|---|---|
| GET | `/api/books` | Get all books (oldest first) | 200 | |
| GET | `/api/books/:id` | Get one book | 200 | 400 invalid id, 404 |
| POST | `/api/books` | Create a book | 201 | 400 validation |
| PATCH | `/api/books/:id` | Update some fields of a book | 200 | 400 validation / invalid id, 404 |
| DELETE | `/api/books/:id` | Delete a book | 204 (empty body) | 400 invalid id, 404 |

Validation (Zod) is the same as in assignment 3:

| Field | POST | PATCH |
|---|---|---|
| `title`, `author`, `genre` | Required, non-empty string (trimmed) | Optional, non-empty string if sent |
| `available` | Optional boolean, defaults to `true` | Optional boolean |
| Unknown fields (e.g. `id`) | Rejected | Rejected |
| Empty body `{}` | Rejected (fields missing) | Rejected (send at least one field) |

Every error uses the same JSON shape:

```json
{
  "error": {
    "message": "Validation failed",
    "details": [
      { "field": "author", "message": "author is required" },
      { "field": "genre", "message": "genre is required" }
    ]
  }
}
```

**One deliberate addition:** an id larger than 2,147,483,647 (for example `/api/books/2147483648`) now returns **400 Invalid book id**. That is the largest value a PostgreSQL `INT` column can hold. Without this check the database query would fail and return a 500. Before, the in-memory version returned 404 for such ids.

**Order of `GET /api/books`:** sorted by `id` (`orderBy: { id: "asc" }`). Without `ORDER BY`, PostgreSQL does not promise any order. With it, the list keeps the same oldest-first order as the old array.

## How to Run

Requirements: Node.js 22+ and PostgreSQL (tested on PostgreSQL 18).

1. **Install** (this also generates Prisma Client):

   ```bash
   cd assignment-5-library-api-prisma
   npm install
   ```

2. **Configure the databases.** Create two empty databases, `library_api_db` and `library_api_test_db` (for example in pgAdmin). Then copy the templates and set your PostgreSQL password in both copies:

   ```bash
   cp .env.example .env
   cp .env.test.example .env.test
   ```

   `.env` and `.env.test` are ignored by Git, so the password is never committed.

3. **Create the table and add the starting books:**

   ```bash
   npx prisma migrate deploy   # applies prisma/migrations to library_api_db
   npm run db:seed             # adds 3 books if the table is empty
   ```

4. **Start the API:**

   ```bash
   npm run dev
   ```

   It runs at `http://localhost:3000/api/books`.

## Testing and Verification

### Automated tests

```bash
npm test   # 22 tests, all passing
```

The tests start the real app on a random port and send real HTTP requests to it. Data goes to a separate PostgreSQL database, `library_api_test_db`, loaded from `.env.test`:
- **Before the tests**, the `books` table is emptied (`TRUNCATE ... RESTART IDENTITY`) and the 3 starting books are added, so every run starts from the same data.
- **Safety check:** the tests stop with an error if `DATABASE_URL` does not point to a database whose name contains `test`. This means a mistake can never wipe the real data. I checked this by running the tests with `.env`: they refused to start.

| Group | Tests | What they check |
|---|---|---|
| The 17 tests from assignment 3 | 17 | Every endpoint, with its success and failure cases. They pass without changes, which shows the contract is preserved. The first test now also checks the exact seeded books from the database |
| New: id too large for `INT` | 1 | Returns 400, not 500 |
| New: data persistence | 4 | After `POST`, `PATCH` and `DELETE`, the test reads the table **directly with Prisma, not through the API**, to prove the change is really in PostgreSQL. A fourth test stops the server, starts a new one, and still finds the book |

### Manual check: persistence across a real restart

On the development database (`library_api_db`):
1. Seeded the 3 starting books and started the server (`node dist/server.js`).
2. `POST /api/books` created `{"id":4,"title":"Persistence Check",...}`.
3. Stopped the server process completely, then started a new one.
4. `GET /api/books` still returned 4 books, including id 4. With the old in-memory version it would have returned only the 3 starting books.
5. Ran `SELECT * FROM books` in `psql`: the same 4 rows. `_prisma_migrations` shows `20261128105419_init` as applied.

### Postman

1. Start the server: `npm run dev`.
2. In Postman, choose **Import** and select `postman/library-book-api.postman_collection.json`.
3. Open the collection and click **Run**, keeping the default order.

It is the same collection as in assignment 3: 12 requests with built-in checks. "Create book" saves the new id, and the requests after it use that id, so the collection works with database ids too. After running it, the created data can be seen in pgAdmin or with `npm run prisma:studio`.
