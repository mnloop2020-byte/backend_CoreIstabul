**Session 4 assignment: AI-Assisted PostgreSQL Database Project.** (Not the Session 4 "Library Book Management API" assignment in `assignment-3-library-book-api`.)

This project is a library database with 4 related tables, sample data, and the queries the assignment asks for: CRUD, JOIN, GROUP BY, pagination, a transaction, and an index evaluation with `EXPLAIN ANALYZE`.

Tested on **PostgreSQL 18** (Windows, `psql`). The output of every file is saved in [`results/`](results/), so each claim below can be checked against a real run.

## Summary: How It Works

**What it is:** a database for a small library. Members borrow books, and each book belongs to an author.

**Tables and relations:**

```text
authors 1 ──< books 1 ──< loans >── 1 members
```

- One author has many books (`books.author_id` → `authors`).
- One book can be loaned many times, and one member can borrow many books. `loans` connects them (`loans.book_id` → `books`, `loans.member_id` → `members`).
- A loan is open while `returned_at` is `NULL`.

**Keeping the data correct:** the database itself rejects bad data, so the rules do not depend on the application code:
- **Primary keys** are generated by PostgreSQL (`GENERATED ALWAYS AS IDENTITY`), so a client cannot choose an id.
- **Foreign keys** with `ON DELETE RESTRICT`: you cannot delete an author who still has books, or a book that has loans.
- **`CHECK`**: copies can never be negative, `available_copies` can never be more than `total_copies`, and a loan cannot be due or returned before it starts.
- **`UNIQUE`**: no two books with the same ISBN, and no two members with the same email.

**Why a transaction is needed:** borrowing a book takes two writes: insert a loan, and lower `available_copies` by 1. If only one of them is saved, the data is wrong. A transaction makes them one unit: both are saved (`COMMIT`) or neither is (`ROLLBACK`).

**Why an index:** PostgreSQL creates indexes for primary keys and `UNIQUE` columns automatically, but **not for foreign keys**. Without an index, "show the loans of member 42" reads every row in `loans`. An index on `loans.member_id` lets PostgreSQL jump straight to that member's rows.

## Schema

| Table | Columns | Rows in sample data |
|---|---|---|
| `authors` | `author_id` PK, `name`, `country`, `created_at` | 8 |
| `books` | `book_id` PK, `title`, `author_id` FK, `genre`, `published_year`, `isbn`, `total_copies`, `available_copies` | 16 |
| `members` | `member_id` PK, `full_name`, `email`, `joined_at` | 10 |
| `loans` | `loan_id` PK, `book_id` FK, `member_id` FK, `loaned_at`, `due_at`, `returned_at` | 15 (8 returned, 7 open, 2 of them overdue) |

### Constraints

| Constraint | Table | Rule |
|---|---|---|
| `PRIMARY KEY` (identity) | all tables | Unique id generated by the database |
| `FOREIGN KEY ... ON DELETE RESTRICT` | `books.author_id`, `loans.book_id`, `loans.member_id` | No row can point to a missing parent, and a parent with children cannot be deleted |
| `NOT NULL` | names, titles, emails, dates | Required fields |
| `UNIQUE` | `books.isbn`, `members.email` | No duplicates |
| `CHECK` | `books` | `total_copies >= 0`, `available_copies >= 0`, `available_copies <= total_copies`, `published_year BETWEEN 1450 AND 2100` |
| `CHECK` | `members.email` | Must look like an email (`'%_@_%'`) |
| `CHECK` | `loans` | `due_at > loaned_at`, `returned_at` is `NULL` or `>= loaned_at` |

### Pagination ([`results/05_pagination.txt`](results/05_pagination.txt))

5 books per page, 16 books, so 4 pages.

| Method | How | Good for | Limitation |
|---|---|---|---|
| `LIMIT / OFFSET` | `LIMIT 5 OFFSET (page - 1) * 5` | Jumping to any page number | PostgreSQL still reads the skipped rows, so deep pages get slow |
| Keyset (cursor) | `WHERE book_id > last_seen_id LIMIT 5` | Infinite scroll, large tables | Only "next page", no jumping to page N |

Both need `ORDER BY`. Without it, PostgreSQL does not guarantee the row order, so pages could overlap or skip rows.

### Transaction ([`results/06_transaction.txt`](results/06_transaction.txt))

| Demo | What happens | Verified result |
|---|---|---|
| 1. `COMMIT` | Noor borrows *The Bastard of Istanbul*: insert a loan and set `available_copies` from 1 to 0 | Both changes saved: 0 copies left, 1 open loan |
| 2. `ROLLBACK` after an error | Noor tries to borrow *And Then There Were None* (0 copies). The loan is inserted, then the `UPDATE` to -1 breaks `CHECK (available_copies >= 0)` | `ROLLBACK` also undoes the loan that was already inserted: 0 loans for Noor on that book, copies still 0 |
| 3. `ROLLBACK` by choice | `DELETE FROM loans` with no `WHERE` (a classic mistake), inside a transaction | 0 loans inside the transaction, 16 again after `ROLLBACK` |

Demo 2 is the main point: without a transaction, the loan would stay in the table even though no copy was available.

## Index Evaluation

**Query:** the loan history of one member, newest first.

```sql
SELECT loan_id, book_id, loaned_at, returned_at
FROM loans
WHERE member_id = 42
ORDER BY loaned_at DESC;
```

**Index:**

```sql
CREATE INDEX idx_loans_member_id ON loans (member_id);
```

**Test data:** an index makes no difference on 15 rows, so [`07_index_explain.sql`](sql/07_index_explain.sql) first adds 5,000 members and 200,000 returned loans with `generate_series` (`setseed` makes the data the same on every run). Member 42 has 45 of the 200,016 loans.

**Results** (from [`results/07_index_explain.txt`](results/07_index_explain.txt)):

| | Without index | With index |
|---|---|---|
| Plan | `Parallel Seq Scan` on `loans` | `Bitmap Index Scan` on `idx_loans_member_id` + `Bitmap Heap Scan` |
| Rows read and thrown away | 199,972 (`Rows Removed by Filter: 99986` × 2 processes) | 0 |
| Pages read (`Buffers`) | 1,705 | 47 |
| Estimated cost | 4,142.83 | 147.68 |
| Execution time | 50.9 ms | 0.5 ms |

**Reading the result:**
- Without the index, PostgreSQL reads every page of the table and checks every row. It even starts a second process (`Parallel`) to share the work.
- With the index, it finds the 45 matching rows in the index (2 pages), then reads only the 45 table pages that hold them.
- **Pages read is the most reliable measure: about 36 times fewer.** Timings change between runs and depend on the cache. Also, part of the 50.9 ms is the cost of starting the parallel worker; the scan itself took about 5 ms. So the "100× faster" figure overstates the gain on this small table.
- **Cost of the index:** it uses 1,432 kB of disk (the table is 13 MB), and every `INSERT`, `UPDATE` and `DELETE` on `loans` must also update it. For a library, the member's loan history is read often, so the trade is worth it.

## How to Run

Requirements: PostgreSQL (tested on 18) and Git Bash.

1. Copy `.env.example` to `.env` and set your PostgreSQL password. `.env` is ignored by Git.
2. Run everything:

   ```bash
   cd assignment-4-postgresql-library-db
   bash run-all.sh
   ```

The script creates the `library_db` database if it does not exist, runs the files in order, and writes each output to `results/`. You can run it again at any time: `01_schema.sql` drops and recreates the tables.

The files can also be run one by one in pgAdmin's Query Tool, in the same order. Run `07_index_explain.sql` last, because its 200,000 test rows change the results of the other queries.

**Key concepts practiced:**
- Using constraints (`FOREIGN KEY`, `CHECK`, `UNIQUE`) so the database itself rejects bad data.
- `INNER JOIN` vs `LEFT JOIN`, and `WHERE` vs `HAVING`.
- `LIMIT/OFFSET` vs keyset pagination.
- A transaction makes several writes all-or-nothing. After an error, PostgreSQL refuses every statement until `ROLLBACK`.
- Foreign keys are not indexed automatically. `EXPLAIN ANALYZE` shows the real plan, and pages read is a more stable measure than time.
